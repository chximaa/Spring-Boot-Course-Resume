PART 01

Monolithic Architecture — The Traditional Way

🏗️ What is a Monolithic Application?

Imagine you are building a huge building — but instead of having separate rooms, you build everything as one giant room. The kitchen, bedroom, bathroom, and office are all the same open space with no walls. That's a monolith.

💡
Simple Definition A monolithic application is ONE single program where ALL the features (user management, products, payments, etc.) live together in the same codebase, are compiled together, and run on the same server.

🔍 How It Works — The 4 Components

🌐

1. Clients (Browsers / Mobile Apps)

These are the users who send requests to your application. Whether it's a browser, a mobile app, or another API — they all send requests to one single address.

🖥️

2. The Monolithic Server (The Giant Brain)

All code is here: the Router, Feature A (User Management), Feature B (Product Catalog), Feature C (Payment). They ALL share the same memory, processor, and are all deployed together.

🔀

3. The Router

The router receives incoming requests and directs them to the correct feature inside the application. Think of it as a receptionist who decides which department handles your request.

🗄️

4. One Shared Database

All features share the same single database. Feature A, B, and C all read and write to the same place. This creates tight coupling between parts of the application.

✅ Advantages of Monolith

AdvantageWhy it helps
Simple to develop at firstYou just write one project — no network calls between services
Easy to deployOne file (a .jar or .war) and you're done
Simpler testingEverything is in one place so you can run all tests together
Fast internal callsFeature A calling Feature B happens in RAM (no network delay)

❌ Disadvantages — Why Monoliths Break Down

ProblemReal-world impact
Hard to scale (Scalability)If Feature A gets heavy traffic, you must duplicate the ENTIRE app — even Features B and C that don't need it. Wasteful!
"Spaghetti code"Over time the codebase becomes huge and tangled. Changing one feature can accidentally break another.
Risky deploymentsChanging ONE line of code in Feature C requires restarting the ENTIRE application — causing downtime for everyone.
Technology lock-inYou're stuck with ONE programming language for everything. Can't write Feature A in Java and Feature B in Python.

📖 Amazon's Real Story

🏪
Amazon Started as a Monolith Amazon's original website was one giant monolithic application. As their team grew, developers spent entire DAYS or WEEKS just merging code changes. Frequent conflicts. Impossible to scale individual features. The solution? They broke their monolith into microservices — and the rest is history.

🔖 Key Points — Chapter 1

  • A monolith = everything in one single deployable unit
  • Great for small projects, terrible for large growing systems
  • The 3 big problems: hard to scale, hard to maintain, risky to deploy
  • Teams are interdependent — slow everyone down
PART 02

Microservices — The Modern Solution

🔬 What is a Microservice?

📌
Official Definition An architecture where the application is broken into a collection of small, independent services, each running its own process and communicating via lightweight mechanisms (usually HTTP/REST).

Instead of one giant room, now you have separate apartments. Each apartment (service) has its own entrance, its own furniture, and its own rules. If one apartment catches fire, the others are not affected.

🧬 Anatomy of a Single Microservice

Each microservice is completely autonomous. It has:

  • Its own business logic — only handles one domain (e.g., only products)
  • Its own libraries — independent dependencies
  • Its own web server — (e.g., embedded Tomcat, Jetty)
  • Its own database — this is the "Database per Service" golden rule
  • Often packaged in Docker — containerized for easy deployment
⚠️
The Golden Rule — Database per Service Each microservice MUST have its own private database. Service A must NEVER directly access the database of Service B. They can only communicate via their APIs. This is what makes them truly independent.

🔑 The 3 Core Principles

🔗

Loose Coupling (Faible couplage)

Simple Definition: Services know as little as possible about each other.

Real-life analogy: You can change a lightbulb without knowing how the entire electrical system of the building works.

In practice: The Payment Service doesn't care how the User Service stores user data — it just calls the User API.

🎯

High Cohesion (Forte cohésion)

Simple Definition: All code related to one topic stays together.

Real-life analogy: All ingredients for a pizza are in the pizza section of a recipe book, not scattered across all chapters.

In practice: All billing logic is in the Billing Service. Not split between three different services.

🚀

Independent Deployment

Simple Definition: I can update Service A without restarting or affecting Service B.

Real-life analogy: Updating the WiFi password doesn't require turning off the entire building's electricity.

📊 Monolith vs. Microservices — Full Comparison

FeatureMonolithMicroservices
SimplicitySimple at start, complex laterComplex infrastructure from day 1
LanguageOne language for everythingEach service can use its own language (Polyglot)
ScalingVertical (buy a bigger server)Horizontal (duplicate only the needed service)
Failure ImpactOne infinite loop crashes the entire appA failure is isolated to one service
DeploymentFull restart needed for any changeDeploy one service at a time
Team StructureTeams depend on each otherEach team owns one service independently
DatabaseOne shared databaseDatabase per service
🕷️
TRAP: The "Distributed Monolith" If Service A always calls Service B, which calls Service C, and if C fails, everything fails — you have NOT gained the benefits of microservices. You just have a slow, complex monolith. The golden rule: minimize synchronous calls between services.

🔖 Key Points — Chapter 2

  • Microservices = many small, independent, autonomous services
  • Each service has its OWN database — never share databases!
  • 3 core principles: Loose Coupling, High Cohesion, Independent Deployment
  • Microservices are great for large teams and large applications
  • Avoid the "distributed monolith" trap — don't chain services synchronously
PART 03

Spring Boot — The Microservice Framework

🤔 What is Spring Boot?

🌱
Simple Definition Spring Boot is a framework (a pre-built toolkit) that makes it very easy to create stand-alone, production-ready Java applications. It packages your application as an executable JAR file — no need to install a separate server!

😩 The Problem Before Spring Boot

In old-school Spring/Java EE, building a simple "Hello World" web application required:

  • Manually installing a server (Tomcat, Glassfish) on your machine
  • Writing multiple XML configuration files (web.xml, persistence.xml)
  • Spending days just setting up "plumbing" before writing any real code
  • XML errors only discovered at runtime — not during compilation

✨ Spring Boot's 3 Major Promises

⚙️

Promise 1: Auto-Configuration

Spring Boot detects what libraries you've added and automatically configures them for you.

Example: You add the H2 database library → Spring Boot automatically creates a DataSource connection for you. Zero lines of configuration code!

This works via the @EnableAutoConfiguration annotation — it scans your class path and says "I see H2! The user probably wants a database. Let me set it up."

Priority rule: Your own configuration always overrides Spring Boot's automatic one.

📦

Promise 2: Autonomous Applications (The Fat JAR)

Before Spring Boot: You generated a .war file and dropped it into a running Tomcat server. The app had to go to the server.

With Spring Boot: The server comes inside the app! Spring Boot bundles your code + all dependencies + an embedded Tomcat server into ONE executable JAR file.

To run your entire app: java -jar myapp.jar — that's it!

📋

Promise 3: Starter Dependencies

Instead of adding 30 individual libraries one by one, Spring Boot gives you Starters — pre-packaged bundles for common tasks.

One line in pom.xml = ~30 compatible libraries installed automatically:

xmlpom.xml — Adding one starter
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
  <!-- This ONE line installs: Tomcat, Jackson (JSON), Spring MVC, and more! -->
</dependency>

📁 Understanding pom.xml — The Project's Identity Card

pom.xml (Project Object Model) is Maven's configuration file at the root of your project. Think of it as your project's birth certificate + shopping list + build recipe.

🔑 The @SpringBootApplication Annotation

This is the most important annotation in your project. It's actually a shortcut for 3 annotations combined:

javaMicrocommerceApplication.java
@SpringBootApplication  // = the 3 annotations below combined
// @Configuration         → This class can define Beans (config objects)
// @EnableAutoConfiguration → Auto-configure everything based on classpath
// @ComponentScan         → Scan packages to find Spring components

  public static void main(String[] args) {
    SpringApplication.run(MicrocommerceApplication.class, args);
    // This one line starts your ENTIRE web server!
  }
}

🔖 Key Points — Chapter 3

  • Spring Boot = Spring Framework + Auto-config + Embedded Server
  • No more XML files — annotations replace configuration
  • Fat JAR = your code + Tomcat + all libraries in ONE file
  • Starters = bundled groups of compatible dependencies
  • @SpringBootApplication = the entry point annotation (3-in-1)
  • pom.xml = your project's identity + dependency list

REST APIs & HTTP Verbs — The Language of Microservices

🍽️ The Restaurant Analogy for REST

Understanding an API with a restaurant analogy:

  • 👤 The Client (You) — You want to order food
  • 🍳 The Kitchen (Database/Server) — Where the food is made, but you can't enter directly
  • 🧑‍💼 The Waiter (REST API) — Takes your request, brings it to the kitchen, brings back your response
📡
REST Definition REST (Representational State Transfer) is an architectural style that uses the HTTP protocol to transfer data between a client and a server. A REST API is a "window" that an application opens to let other programs communicate with it.

🔡 JSON — The Universal Language

REST APIs don't return HTML pages. They return raw data in JSON format.

jsonExample API Response
{
  "id": 1,
  "nom": "Ordinateur Portable",
  "prix": 350
}

JSON is lightweight, human-readable, and understood by every language (Java, Python, JavaScript, etc.).

PART 06

Controllers & Returning JSON — The Code

📦 Step 1 — Create the Product Model

A Model represents the data your microservice manages. In Java, it's a Plain Old Java Object (POJO) / JavaBean.

📏
JavaBean Rules (Golden Rules of a Bean) 1. Private attributes (encapsulation) | 2. Public no-argument constructor | 3. Getters and Setters for each attribute | 4. (Optional) toString() method
javaProduct.java (Model class)
package com.ecommerce.microcommerce.model;

public class Product {

    // RULE 1: Private attributes — protect the data
    private int id;
    private String nom;     // "nom" = "name" in French
    private int prix;     // "prix" = "price" in French

    // RULE 2: No-argument constructor (required by Jackson for JSON)
    public Product() {}

    // Constructor with all fields
    public Product(int id, String nom, int prix) {
        this.id = id;
        this.nom = nom;
        this.prix = prix;
    }

    // RULE 3: Getters and Setters
    public int getId() { return id; }
    public void setId(int id) { this.id = id; }

    public String getNom() { return nom; }
    public void setNom(String nom) { this.nom = nom; }

    public int getPrix() { return prix; }
    public void setPrix(int prix) { this.prix = prix; }

    // RULE 4 (optional): toString for debugging
    @Override
    public String toString() {
        return "Product{" + "id=" + id + ", nom='" + nom + ", prix=" + prix + '}';
    }
}

🕹️ Step 2 — Create the REST Controller

The Controller is the "brain" of your microservice. It listens for HTTP requests and sends back responses.

javaProductController.java
package com.ecommerce.microcommerce.web.controller;

import com.ecommerce.microcommerce.model.Product;

@RestController  // = @Controller + @ResponseBody
// @Controller  → This class handles HTTP requests
// @ResponseBody → Send return value as JSON (not HTML)
public class ProductController {

    // ✅ GET /Produits — Returns the list of all products
    @GetMapping(value = "/Produits")
    public List<Product> listeProduits() {
        // For now: return a hard-coded list. Later: use DAO
        return Arrays.asList(
            new Product(1, "Ordinateur portable", 350),
            new Product(2, "Aspirateur Robot", 500),
            new Product(3, "Table de Ping Pong", 750)
        );
    }

    // ✅ GET /Produits/{id} — Returns ONE product by its ID
    @GetMapping(value = "/Produits/{id}")
    public Product afficherUnProduit(@PathVariable int id) {
        // {id} in URL → @PathVariable maps URL value to Java variable
        // Example: /Produits/42 → id = 42
        return new Product(id, "Aspirateur", 100);
    }
}

🔑 Key Annotations Explained

AnnotationWhat it doesWhen to use
@RestControllerMarks this class as a REST endpoint handler. All methods return JSON automatically.On every controller class
@GetMapping("/path")Maps this method to GET requests at the given pathFor READ operations
@PostMapping("/path")Maps this method to POST requestsFor CREATE operations
@PutMapping("/path")Maps this method to PUT requestsFor UPDATE operations
@DeleteMapping("/path")Maps this method to DELETE requestsFor DELETE operations
@PathVariableExtracts a value from the URL pathWhen URL has {variable}

⚡ How JSON Conversion Works (The Jackson Magic)

When your method returns a Product object, Spring Boot uses a library called Jackson to automatically convert it to JSON:

Product object
Java Object in memory
→
Jackson reads Getters
getId() → "id": 1
→
{ "id":1, "nom":"...", "prix":350 }
JSON string sent to client

The reverse also happens: Jackson reads incoming JSON and calls your Setters to populate a Java object (Deserialization).

🔖 Key Points — Chapter 6

  • @RestController = marks a class as a REST handler. Automatically returns JSON.
  • @GetMapping, @PostMapping, etc. = bind HTTP verbs to methods
  • @PathVariable = extracts values from the URL (e.g., /Produits/{id})
  • Jackson automatically converts Java objects ↔ JSON
  • The Model class (Product) must be a proper JavaBean for Jackson to work

The DAO Pattern — Separating Data from Logic

🤔 What is a DAO?

🗃️
DAO = Data Access Object It's a design pattern (a smart structural solution) that separates your data access logic from your business logic. Instead of the Controller directly accessing the database, it asks the DAO to do it.

Real-life analogy: You don't go to the library's storage room to find a book yourself. You ask the librarian (DAO). The librarian knows where everything is stored and retrieves it for you.

📐 Why Use a DAO?

  • Separation of concerns: Controller handles HTTP, DAO handles data storage
  • Database independence: Switch from an ArrayList to MySQL by only changing the DAO
  • Reusability: Multiple controllers can use the same DAO
  • Testability: You can test the controller without a real database

📝 Step 1 — Define the Interface (The Contract)

javaProductDao.java (Interface)
package com.ecommerce.microcommerce.dao;

public interface ProductDao {

    // CONTRACT: Anyone who implements this interface MUST provide these methods

    List<Product> findAll();        // Returns all products

    Product findById(int id);       // Find one product by ID

    Product save(Product product); // Save (add or update) a product
}
✨
Why these specific method names? findAll, findById, save are Spring standard naming conventions. Later, Spring Data JPA will automatically generate the SQL for these methods just by reading their names!

🔨 Step 2 — Implement the DAO (The Simulated Database)

javaProductDaoImpl.java
@Repository  // Tells Spring: "This class handles data access — create a Bean of it"
             // Spring also translates DB exceptions into Java exceptions
public class ProductDaoImpl implements ProductDao {

    // static = this list is SHARED by ALL instances
    // If User A adds a product, User B sees it too (until server restarts)
    private static List<Product> products = new ArrayList<>(Arrays.asList(
        new Product(1, "Ordinateur portable", 350),
        new Product(2, "Aspirateur Robot", 500),
        new Product(3, "Table de Ping Pong", 750)
    ));

    @Override
    public List<Product> findAll() {
        return products;  // Simply returns the full list
    }

    @Override
    public Product findById(int id) {
        for (Product p : products) {      // Loop through the list
            if (p.getId() == id) return p; // Return if ID matches
        }
        return null;  // Not found → return null (we'll fix this later)
    }

    @Override
    public Product save(Product product) {
        products.add(product);  // Add the product to the list
        return product;          // Return the saved product
    }
}

🔌 Step 3 — Inject the DAO into the Controller (Dependency Injection)

💉
Dependency Injection (DI) Instead of creating objects yourself with new ProductDaoImpl(), you let Spring create them and give them to you automatically. This is "Inversion of Control" — Spring controls the object creation.
javaProductController.java — With DAO Injection
@RestController
public class ProductController {

    // final = once set in constructor, never changes (safe)
    private final ProductDao productDao;

    // Constructor Injection — Spring sees this and automatically
    // provides the @Repository-annotated ProductDaoImpl instance
    public ProductController(ProductDao productDao) {
        this.productDao = productDao;
    }

    @GetMapping("/Produits")
    public List<Product> listeProduits() {
        return productDao.findAll();  // Now uses the DAO!
    }

    @GetMapping("/Produits/{id}")
    public Product afficherUnProduit(@PathVariable int id) {
        return productDao.findById(id);
    }

    @PostMapping("/Produits")
    public Product ajouterProduit(@RequestBody Product product) {
        // @RequestBody converts incoming JSON → Java Product object
        return productDao.save(product);
    }
}

PART 09

JPA & Data Persistence — Making Data Survive Restarts

❓ Why Do We Need a Database?

💀
The Amnesia Problem Our ArrayList-based microservice is "amnesic." Every time you restart the server, ALL data disappears. Products added via POST? Gone. This is because RAM (memory) is volatile — it clears when the program stops.

A database is like a filing cabinet outside of the microservice. Even if the microservice shuts down, the files (data) stay in the cabinet. When it restarts, it finds everything exactly as it left it.

🤝 The Mismatch: Java Objects vs. SQL Tables

Java and SQL speak different languages. This is called the Object-Relational Impedance Mismatch:

IssueJava WorldSQL World
Naming ConventionstargetDate (camelCase)target_date (snake_case)
RelationshipsList<Employee> inside a classJoin tables with foreign keys
InheritanceFullTimeEmployee extends EmployeeNot natively supported — needs one flat table
Data unitObjects with methods & behaviorRows & columns — only data

🔧 What is JPA (Java Persistence API)?

📋
JPA = A Specification (a set of rules) JPA defines HOW Java should work with databases. It doesn't implement the work itself — it just defines the rules. The implementation is done by Hibernate.

Analogy: JPA = the traffic code (rules), Hibernate = the car (the thing that actually drives).

📊 The Persistence Technology Stack (History)

TechnologyWhat you had to doPain level
JDBC (raw)Open connection manually, write SQL as strings, parse ResultSet row by row with rs.getString("col")😫 Very painful
Spring JDBC TemplateLess boilerplate, but still writing raw SQL strings😐 Better, but SQL is still manual
MyBatisSQL in external XML files, objects auto-populated🙂 Good, but 1000s of SQL files in large apps
JPA + HibernateZero SQL — annotate your class, JPA generates queries😍 Developer-friendly
Spring Data JPAEven less — just an interface, Spring generates everything🤩 Near-zero code

🏷️ JPA Core Concepts

🗂️

Entity — The Java Mirror of a SQL Table

An Entity is a Java class annotated with @Entity. It tells JPA: "This class represents a table in my database."

If the class is called Product, JPA creates/uses a table called product.

📋

ORM — Object-Relational Mapping (The Translator)

ORM automatically translates between Java and SQL:

  • 1 Java class → 1 SQL table
  • 1 Java object instance → 1 row in the table
  • 1 Java attribute → 1 column in the table

🏷️ Essential JPA Annotations

javaProduct.java — JPA Entity
@Entity                  // "This class maps to a DB table"
@Table(name = "product") // Optional: specify exact table name
public class Product {

    @Id                    // This field is the primary key
    @GeneratedValue(strategy = GenerationType.IDENTITY)
                           // Auto-increment the ID (1, 2, 3...)
    private int id;

    @Column(name = "nom")  // Optional: maps to column "nom"
    @Size(min = 3)          // Validation: name must be at least 3 chars
    private String nom;

    @Min(1)                 // Validation: price must be at least 1
    private int prix;

    // constructors, getters, setters...
}

⚡ The 4 EntityManager Operations

MethodActionSQL GeneratedAnalogy
persist(obj)Insert new objectINSERT INTO ...Adding a new contact to phonebook
merge(obj)Update existing objectUPDATE ... SET ...Editing a contact's number
remove(obj)Delete objectDELETE FROM ...Deleting a contact
find(class, id)Find object by IDSELECT * WHERE id=?Searching contact by name

🔖 Key Points — Chapter 9

  • ArrayList data disappears on restart → need a real database
  • JPA = the specification (rules). Hibernate = the implementation (engine)
  • ORM = the translator: Java class ↔ SQL table, Java object ↔ SQL row
  • @Entity = marks a class as a DB table, @Id = marks the primary key
  • H2 = a lightweight in-memory database, perfect for development/testing
PART 10

Spring Data JPA — Zero-Code Database Access

😅 The Problem with Raw JPA (EntityManager)

If you have 50 Entity classes (Product, Order, Payment, User...) you'd need to write 50 DAO implementation classes, each with the same repetitive methods. That's hundreds of lines of copy-paste code.

🚀 The Spring Data JPA Solution

✨
The Magic: Just extend JpaRepository You don't write any implementation class. You just declare an interface that extends JpaRepository, and Spring generates ALL the SQL code automatically at startup!

🔑 The Persistence Pyramid

Your Application
Spring Data JPA → interfaces (findAll, save...)
JPA → The standard rules
Hibernate → The engine that translates
JDBC → The physical pipe to the DB
Database (H2 / MySQL / PostgreSQL...)

📝 Step 1 — Add Dependencies

xmlpom.xml — Add these 2 dependencies
<!-- Spring Data JPA + Hibernate -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>

<!-- H2 embedded database (for development/testing) -->
<dependency>
  <groupId>com.h2database</groupId>
  <artifactId>h2</artifactId>

🪄 Query Derivation from Method Names

Spring Data JPA can generate SQL just from the name of the method you declare in the interface:

javaProductDao.java — Method-name magic
public interface ProductDao extends JpaRepository<Product, Integer> {

    // Just declare this method name — Spring writes the SQL for you!
    List<Product> findByPrixGreaterThan(int prixLimit);
    // ↑ Generated SQL: SELECT * FROM product WHERE prix > ?
    // breakdown: findBy=SELECT, Prix=column, GreaterThan=operator(>)

    List<Product> findByNomContaining(String keyword);
    // Generated SQL: SELECT * FROM product WHERE nom LIKE '%keyword%'

    List<Product> findByNomAndPrix(String nom, int prix);
    // Generated SQL: SELECT * FROM product WHERE nom=? AND prix=?
}

📝 Custom Queries with @Query (JPQL)

For complex queries that don't fit method naming, use @Query with JPQL:

javaProductDao.java — Custom @Query
@Query("SELECT p FROM Product p WHERE p.prix > :prixLimit")
// ^ JPQL: uses Java CLASS names, not SQL table names!
// Product = Java class, not the "product" SQL table
List<Product> findExpensiveProducts(@Param("prixLimit") int prix);
//                               ↑ @Param bridges ":prixLimit" → Java variable "prix"
📡
JPQL vs SQL JPQL (Java Persistence Query Language) is like SQL but targets Java classes instead of SQL tables. FROM Product p means "from the Product Java class". Hibernate then translates this to the correct SQL for your specific database (H2, MySQL, Oracle, etc.).

PART 11

3-Layer Architecture — The Professional Structure

🏗️ The 3 Tiers

A well-structured Spring Boot application is organized into 3 layers, each with a specific responsibility:

🌐

Layer 1 — API Tier (Controllers)

Annotation: @RestController

Job: Listen for HTTP requests, convert JSON ↔ Java objects, validate input, delegate to Service layer.

Golden rule: A controller must contain ZERO business logic. No price calculations, no discount rules — only HTTP handling.

🧠

Layer 2 — Service Tier (Business Logic)

Annotation: @Service

Job: Apply business rules (calculate VAT, check permissions, apply discounts). This layer is independent of HTTP — it can be reused by REST APIs, mobile apps, or scheduled tasks.

Example: "Can this user delete this product?", "What is the total price with tax?"

💾

Layer 3 — Persistence Tier (Repository + Entity)

Components: @Entity classes + JpaRepository interfaces

Job: Bridge between Java and SQL. The Entity mirrors the DB table. The Repository performs CRUD operations.

🎯 Why 3 Layers? The 3 Big Benefits

BenefitHow it helps
MaintainabilityChange from H2 to MySQL? Only modify the Persistence layer. Zero changes in Controller or Service.
TestabilityTest business logic (Service) without starting a web server or database (using Mocks).
ReusabilityMultiple Controllers can share the same Service. Multiple Services can share the same Repository.

🔗 Complete CRUD Implementation

javaProductController.java — Full CRUD with Spring Data JPA
@RestController
public class ProductController {

    private final ProductDao productDao;  // Spring injects this

    public ProductController(ProductDao productDao) {
        this.productDao = productDao;
    }

    // ✅ READ ALL
    @GetMapping("/Produits")
    public List<Product> listeProduits() {
        return productDao.findAll();
    }

    // ✅ READ ONE — with error handling
    @GetMapping("/Produits/{id}")
    public Product afficherUnProduit(@PathVariable int id) {
        Product p = productDao.findById(id).orElse(null);
        if (p == null) throw new ProduitIntrouvableException("Produit introuvable: " + id);
        return p;
    }

    // ✅ CREATE
    @PostMapping("/Produits")
    @ResponseStatus(HttpStatus.CREATED)  // Return 201 instead of 200
    public Product ajouterProduit(@Valid @RequestBody Product product) {
        // @Valid triggers validation annotations (@Size, @Min) in Product
        // If invalid: Spring returns 400 Bad Request automatically
        return productDao.save(product);  // INSERT INTO product...
    }

    // ✅ UPDATE
    @PutMapping("/Produits")
    public Product updateProduit(@RequestBody Product product) {
        // .save() with an existing ID = UPDATE (not INSERT)
        return productDao.save(product);
    }

    // ✅ DELETE
    @DeleteMapping("/Produits/{id}")
    public void supprimerProduit(@PathVariable int id) {
        productDao.deleteById(id);  // DELETE FROM product WHERE id=?
    }
}

Error Handling & Validation

🐛 The Problem: Lying API

If a client requests GET /Produits/999 and product 999 doesn't exist, our API currently returns 200 OK with an empty body. This is wrong! 200 means "success" — but nothing was found. The API is lying.

🏗️ Step 1 — Create a Custom Exception

javaProduitIntrouvableException.java
package com.ecommerce.microcommerce.web.exceptions;

@ResponseStatus(HttpStatus.NOT_FOUND)  // Maps this exception → HTTP 404
public class ProduitIntrouvableException extends RuntimeException {
    // RuntimeException = error that happens during execution

    public ProduitIntrouvableException(String message) {
        super(message);  // Pass the message to the parent class
        // Spring captures this and puts it in the error response
    }
}

🔒 Step 2 — Add Validation Rules to the Model

javaProduct.java — With Validation
// First add to pom.xml:
// <artifactId>spring-boot-starter-validation</artifactId>

@Entity
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private int id;

    @Size(min = 3, message = "Le nom doit avoir au moins 3 caractères")
    // ^ If name has less than 3 chars: reject the request
    private String nom;

    @Min(value = 1, message = "Le prix doit être supérieur à 0")
    // ^ If price is 0 or negative: reject the request
    private int prix;
}

✅ Step 3 — Activate Validation in the Controller

javaProductController.java — @Valid activates the rules
@PostMapping("/Produits")
@ResponseStatus(HttpStatus.CREATED)
public Product ajouterProduit(
    @Valid        // ← This triggers the @Size and @Min checks!
    @RequestBody Product product
) {
    // If @Valid fails: Spring automatically returns 400 Bad Request
    // with details about which field failed which rule
    return productDao.save(product);
}

🔖 Key Points — Chapter 12

  • Never return 200 OK when a resource doesn't exist — use 404
  • Reserve 500 for actual code crashes, not missing data
  • @ResponseStatus on an exception class links it to an HTTP code
  • @Valid activates validation rules defined in the model
  • Validation rules: @Size, @Min, @NotNull, @Email, etc.

Part A — Multiple Choice Questions

Question 01

What is the main disadvantage of a monolithic architecture for large systems?

  • A) It is too simple to build
  • B) Scaling one feature requires scaling the entire application
  • C) It always needs a separate web server
  • D) It can only be written in Python
✅ Correct: B — In a monolith, if Feature A gets heavy traffic, you must duplicate the ENTIRE application, even Features B and C that don't need scaling. Microservices solve this by letting you scale individual services.

What does @RestController actually combine?

✅ Correct: B — @Controller enables request handling, @ResponseBody tells Spring to serialize return values directly as JSON (instead of looking for a view template).

  • D) @RequestHeader
✅ Correct: C — @PathVariable maps a URL template variable like {id} to a Java method parameter.

What is the role of Jackson in Spring Boot?

  • A) Automatically converts Java objects to JSON (and back)
  • B) It is the embedded web server
  • C) It manages the database connection
  • D) It handles HTTP routing
✅ Correct: A — Jackson is a serialization/deserialization library. It reads Java object Getters to produce JSON, and calls Setters when parsing incoming JSON.

In Spring Data JPA, if you call productDao.save(product) with an existing ID, what happens?

  • A) Throws a DuplicateKeyException
  • B) Creates a new product with a new ID
  • C) Updates the existing product (generates UPDATE SQL)
  • D) Deletes the old product and inserts a new one
✅ Correct: C — Spring Data JPA's .save() is smart. If the ID already exists in the DB, it generates an UPDATE. If the ID is new or null, it generates an INSERT.
Question 06

What HTTP status code should you return when a product is not found in the database?

  • A) 200 OK with an empty body
  • B) 500 Internal Server Error
  • C) 404 Not Found
  • D) 204 No Content
✅ Correct: C — 404 Not Found is the standard HTTP code for "the resource you requested doesn't exist." 500 is only for real server crashes. 200 with empty body is actively misleading!
Question 07

What is the relationship between JPA and Hibernate?

  • A) JPA is an implementation of Hibernate
  • B) JPA is the specification (rules), Hibernate is one implementation of those rules
  • C) They are the same thing with different names
  • D) Hibernate is the replacement for JPA
✅ Correct: B — JPA defines the API and annotations (@Entity, @Id...). Hibernate provides the actual engine that reads those annotations and generates SQL. Analogy: JPA = traffic code, Hibernate = the car.

Part B — Short Answer

Question 08 — Define

In your own words, what is the "Database per Service" rule in microservices?

Each microservice must own its private database. No other service can directly access it. Services can only communicate through their APIs. This ensures true independence — if Service A's DB schema changes, Service B is completely unaffected.
Question 09 — Explain

Explain the difference between @RequestBody and @PathVariable. When do you use each?

@PathVariable extracts a value from the URL path itself. Example: /Produits/{id} → @PathVariable int id extracts "42" from /Produits/42. @RequestBody reads the entire JSON body of the request and converts it to a Java object. Example: POST /Produits sends JSON in the body → @RequestBody Product product creates a Product Java object from that JSON. Rule: Use @PathVariable for resource identification in the URL. Use @RequestBody when you're sending a complete data object (for creation/update).
Question 10 — Trace

Trace the full execution path when a client sends POST /Produits with JSON {"nom":"iPad","prix":800}.

1. Client sends POST HTTP request with JSON body to /Produits 2. Spring's Dispatcher Servlet receives the request and routes it to ProductController.ajouterProduit() 3. @RequestBody triggers Jackson to deserialize JSON → calls setNom("iPad") and setPrix(800) on a new Product object 4. @Valid checks the annotations in Product class (@Size, @Min) — if they fail, 400 is returned immediately 5. productDao.save(product) is called 6. Spring Data JPA Proxy generates INSERT INTO product (nom, prix) VALUES ('iPad', 800) 7. Hibernate executes the SQL against H2 database 8. The new product (with auto-generated ID) is returned 9. Jackson serializes the Product object to JSON 10. Spring sends 201 Created response with the JSON body to the client
